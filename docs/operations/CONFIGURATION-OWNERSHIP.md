# Cross-app configuration ownership (0095)

This inventory describes the current integrated Restaurant → Motoboy deployment. It does not implement an independent Motoboy account mode.

## Authority classes

- `RESTAURANT_OWNED`: the Restaurant/server is the sole writer; Motoboy receives only the subset needed for its assigned operation.
- `DRIVER_OWNED`: a future driver-authoritative preference/profile. No server-owned Driver identity is writable from the Motoboy today; the current Driver record remains administered by Restaurant.
- `SHARED_WITH_FIELD_OWNERSHIP`: shared entity whose fields have explicit per-field writers in `CONTRACT.md` (for example Delivery planning vs execution facts).
- `DEVICE_LOCAL`: per-device presentation, navigation, or operational convenience that must not overwrite server settings.
- `DEPLOYMENT_ONLY`: server, database, adapter endpoints, credentials, secrets, runtime roles, and infrastructure policy. Never presented as normal operator configuration.

## Current ownership coverage

`DRIVER_OWNED` applies to the personal financial daily goal; it is persisted by the Motoboy and intentionally is not synchronized to Company or converted to an Earning. Driver identity/profile itself remains `RESTAURANT_OWNED`; per-device GPS, alerts, browser choice, route display and convenience preferences are `DEVICE_LOCAL`. This creates no second authority for Driver identity. `SHARED_WITH_FIELD_OWNERSHIP` applies to the existing `Delivery`/execution contract, not to Company settings.

## Synchronization and conflict rules

- Restaurant Company settings travel in `companySettings` on authenticated Motoboy `/sync/pull`; tenant identity comes from the authenticated principal, not request-supplied `companyId`.
- Motoboy validates tenant, authority, revision and coordinates. It stores the latest valid revision separately from local settings and ignores old revisions. Invalid snapshots fail the pull page rather than being partially applied.
- The Company/Driver controls are read-only for any tenant-linked Motoboy session. Settings command filtering also drops legacy Company/Driver fields, even if a UI control is changed programmatically. Separate `DEVICE_LOCAL` choices remain writable offline.
- Syncing a later Company revision never overwrites local theme, navigation, GPS, print, alert, or simulator preferences. Existing local fields remain for offline compatibility but are not canonical when a tenant session is present.
- No generic last-write-wins is used for Company location/profile. A Company snapshot revision advances on profile, timezone, and location changes; location also carries a separate location revision for Route staleness checks. Company location changes invalidate route decisions that used the old location version; unrelated Company profile edits do not.
- Restaurant dashboard and analytics only display configuration; editing belongs in Settings.

## Stable baseline and consolidation

The stable Restaurant UI baseline already had Settings → Geral with establishment address and map coordinates in local IndexedDB. This campaign extends that existing source into the canonical Company record, preserving the local copy for offline use. It does not introduce a second establishment-location control. The route-origin setting continues to select either this source or a separate custom Route origin.

## Future independent Motoboy mode (not implemented)

A standalone Motoboy would need a distinct Company/tenant and membership lifecycle; independent authentication/authorization and billing relationship; explicit ownership for Driver profile, device preferences, deliveries and earnings; a separate sync topology and conflict contract; and a clear policy for whether Routes belong to the independent courier business or remain Restaurant-controlled. Current `Route` is Restaurant-owned and current `Delivery` is shared with field ownership, so an independent mode cannot be enabled merely by removing read-only controls. No speculative abstraction or migration for that mode is added here.
